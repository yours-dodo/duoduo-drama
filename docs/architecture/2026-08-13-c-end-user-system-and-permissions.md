# C 端用户系统与权限设计

## 文档状态

- 状态：规划中
- 范围：C 端用户、个人空间、团队空间、团队角色、项目协作权限
- 不包含：Admin 后台账号、平台级角色、运营权限
- 关联领域词汇：[根目录 CONTEXT.md](../../CONTEXT.md)

本文档描述目标模型，不代表相关功能已经全部实现。当前 Server 已经存在用户、会话、团队、团队成员、邀请、项目协作者和审计基础，后续实现应在现有模型上渐进迁移。

## 一、产品规则

### 用户与空间

- 用户注册后默认不属于任何团队。
- 每个用户拥有一个全局唯一的个人空间。
- 用户加入多少个团队，都共用同一个个人空间。
- 个人空间第一阶段为私有空间，不直接提供协作者关系。
- 用户可以创建多个团队。
- 创建团队的用户自动成为该团队的 `admin`。
- 团队可以邀请用户加入，邀请本身不直接授予团队访问权。
- 用户加入团队后，同时拥有自己的个人空间和该团队的团队空间。

### 项目归属

- 一个项目属于个人空间或一个团队空间，由项目所有者设置。
- 项目所有者是独立的业务状态，不等同于项目创建者，也不随空间归属自动改变。
- 项目进入团队空间后，获得团队空间权限。
- 项目移入团队空间前，所有者必须是该团队有效成员，并拥有目标团队的 `project.create` 权限。
- 项目从团队空间移回个人空间时，只能移回当前项目所有者自己的个人空间。
- 项目所有者可以将项目所有权转让给团队内其他有效成员。
- 项目所有者退出团队后，项目可以继续留在原团队空间。
- 项目所有者退出团队后，团队管理员可以复制项目；不能因为复制而改变原项目所有权。

### 项目副本

- 团队管理员可以将团队空间项目复制到自己的个人空间。
- 复制后生成一个全新的项目身份。
- 副本所有者和创建者都是复制者。
- 副本与原项目完全独立，不保留运行时关联。
- 副本不继承原项目的团队成员关系、协作者、权限覆盖和团队管理员权限。
- 原项目后续的修改、归档、所有权转让不会影响副本。

## 二、团队角色

第一阶段采用固定内置团队角色，不支持用户自定义团队角色。

| 角色 | 定位 | 默认能力 |
| --- | --- | --- |
| `admin` | 团队管理员 | 管理成员和邀请、修改团队设置、查看团队审计；对团队空间内所有项目隐式拥有 `manager` 能力 |
| `member` | 普通团队成员 | 可以访问团队空间项目的默认查看范围；其他能力由明确的团队权限和项目授权决定 |

团队规则：

- 每个团队必须始终保留至少一个有效 `admin`。
- `admin` 的项目管理权限不写入 `project_collaborators`，而是在授权计算时由团队成员关系隐式得到。
- 团队角色不直接等同于项目编辑权限。
- `project.create` 作为独立的团队级权限判断；项目所有者只有在拥有该权限时，才能把个人项目移入团队空间。

## 三、项目协作角色与能力

项目协作角色只有三种：

| 角色 | 定位 |
| --- | --- |
| `viewer` | 基础查看角色 |
| `editor` | 基础编辑角色，但具体编辑能力可逐人控制 |
| `manager` | 基础项目管理角色，但具体管理能力可逐人控制 |
| `owner` | 项目所有者状态，不作为普通协作者角色 |

项目可以邀请多个团队成员协作。每个协作者的权限独立管理，可以授予、调整和撤销；一个协作者的权限变化不影响其他协作者。

建议的能力目录：

```text
project.view
project.edit
project.generate
project.manage_collaborators
project.archive
project.copy
project.transfer_ownership
project.move_space
```

授权规则：

- `viewer / editor / manager` 是基础角色，不是不可变的完整权限集合。
- 项目所有者可以为每个协作者单独授予或撤销具体能力。
- `editor` 是否可以编辑具体内容、发起生成或归档，由该协作者的实际能力配置决定。
- `manager` 的具体项目管理能力同样可以控制。
- `archive` 是独立能力，不是 `editor` 的固定权限。
- 项目所有者拥有全部项目能力。
- `project.transfer_ownership` 和 `project.move_space` 只能由项目所有者执行。
- 团队 `admin` 对本团队空间项目隐式拥有项目管理能力，不需要项目协作者记录。

有效权限可以抽象为：

```text
有效权限 = 团队角色隐式权限
         + 项目协作基础角色权限
         + 协作者 allow 能力
         - 协作者 deny 能力
```

最终实现必须明确冲突规则。建议采用 `deny` 优先于角色默认能力，但项目所有者和团队 `admin` 的系统级管理边界不受普通协作者覆盖影响。

## 四、项目归档

产品语义使用“归档”，不使用用户侧“删除”作为主要操作名称。

- 项目所有者可以归档项目。
- 团队 `admin` 默认可以归档团队空间项目。
- 具有 `project.archive` 能力的 `manager` 或 `editor` 可以归档项目。
- `viewer` 不能归档项目。
- 归档是软删除，项目进入回收站。
- 项目归档后保留 30 天。
- 30 天内可以恢复，恢复到归档前的原空间。
- 超过 30 天由系统任务硬删除项目及其子数据。
- 硬删除是系统清理行为，不作为普通用户权限。

建议项目保留以下状态字段：

```text
status
archived_at
archive_purge_at
archived_by_user_id
```

归档、恢复和硬删除都应写入审计记录；硬删除前需要保证关联的对象存储文件、对话、消息、成果和其他项目子数据有明确清理策略。

## 五、目标数据库模型

### `users`

现有用户表继续作为全局身份表，建议逐步补充用户资料和状态字段：

```text
id
email
password_hash
display_name
avatar_url
status                 active / disabled
last_login_at
created_at
updated_at
```

登录挑战、会话、密码凭证和身份安全事件继续归属于身份模块，不与项目授权表混合。

### `spaces`

新增统一空间表，表示个人空间和团队空间：

```text
id
kind                   personal / team
owner_user_id          personal 空间使用
owner_team_id          team 空间使用
created_at
updated_at
```

约束：

- `personal` 空间必须且只能属于一个用户。
- `team` 空间必须且只能属于一个团队。
- 一个用户只能有一个个人空间。
- 一个团队只能有一个团队空间。
- `owner_user_id` 与 `owner_team_id` 应通过数据库约束或事务规则保证互斥。

### `teams`

保留现有团队表：

```text
id
name
created_by_user_id
created_at
updated_at
```

团队空间通过 `spaces.owner_team_id` 关联团队。

### `team_memberships`

保留现有成员关系并将角色语义稳定为：

```text
id
team_id
user_id
role                   admin / member
joined_at
removed_at
```

需要保留 `(team_id, user_id)` 唯一约束，并对有效成员和最后一个管理员的并发变更加锁或使用事务保证。

### `team_invitations`

保留现有团队邀请表。邀请应继续使用一次性、限时、不可逆的凭证摘要，不在数据库中保存原始邀请令牌。

邀请流程：

```text
管理员创建邀请
    -> 指定邮箱收到邀请
    -> 对应用户接受邀请
    -> 创建或恢复 member 成员关系
```

管理员角色应通过后续成员管理操作授予，不由普通邀请凭证直接授予。

### `story_projects`

目标项目表建议从“通过 `tenant_id` 表示项目归属”调整为“通过 `space_id` 表示项目归属”：

```text
id
space_id
created_by_user_id
owner_user_id
title
status
archived_at
archive_purge_at
archived_by_user_id
revision
created_at
updated_at
```

字段语义：

- `created_by_user_id`：创建项目的历史事实，不因转让改变。
- `owner_user_id`：当前项目所有者，可以转让。
- `space_id`：项目当前归属的个人空间或团队空间。
- `status`：至少支持 `active` 和 `archived`。

当前代码中的 `visibility = private/team` 更接近空间归属，应在迁移时改为明确的 `space_id` 关系；如需兼容旧接口，可以在应用层暂时映射，避免让 `visibility` 同时承担归属和权限含义。

### `project_collaborators`

建议扩展现有项目协作者表：

```text
id
project_id
user_id
role                     viewer / editor / manager
created_at
updated_at
revoked_at
```

约束：

- 一个项目同一时间只能有一条有效的用户协作者关系。
- 协作者必须是该项目所属团队的有效成员。
- 个人空间项目第一阶段不创建协作者关系。
- 项目移回个人空间后，原团队协作者关系不再产生访问权；建议保留并标记为失效，便于审计和再次移入团队时决定是否恢复。

### `project_collaborator_permission_overrides`

用于实现逐人动态控制：

```text
id
collaborator_id
permission_key
effect                   allow / deny
granted_by_user_id
created_at
updated_at
```

`permission_key` 应引用受控的系统权限目录，而不是允许任意字符串无限扩张。第一阶段至少覆盖 `project.archive`，后续可增加编辑、生成和协作者管理等能力。

### 项目子表

`conversations`、`messages`、`assets`、`story_artifacts` 等项目子数据应通过项目的 `space_id` 间接确定访问边界。

迁移阶段可以暂时保留 `tenant_id` 作为团队查询和数据隔离的冗余字段，但必须允许个人项目没有团队归属，并禁止业务代码继续把所有项目当作团队项目处理。

### 权限目录表（可选）

如果希望将角色权限从代码常量迁移为可审计的系统配置，可以增加：

```text
permissions
roles
role_permissions
```

第一阶段不开放自定义角色。上述表只保存系统内置角色和权限种子，协作者逐人差异仍通过 `project_collaborator_permission_overrides` 保存。

## 六、授权判断边界

授权应集中在 Server 的领域和应用层，Agent 不拥有用户授权，也不直接访问 Server 数据库。

建议按以下顺序判断：

1. 验证用户会话和用户状态。
2. 确定请求目标项目及其 `space_id`。
3. 如果是个人空间，只允许项目所有者访问。
4. 如果是团队空间，验证用户是否为该团队有效成员。
5. 计算团队 `admin` 的隐式权限。
6. 读取项目协作者基础角色和能力覆盖。
7. 应用项目所有者专属规则、归档状态和操作级限制。
8. 在同一事务中执行状态变化并写入审计记录。

所有项目读写、生成、归档、恢复、复制、移入团队、移回个人空间、转让所有权和协作者变更，都应经过同一套授权策略，不能在 Controller 中各自实现一套判断。

## 七、实施顺序

建议拆分为以下阶段：

1. 稳定领域类型：`Space`、`ProjectOwner`、团队角色、项目协作角色和能力目录。
2. 增加个人空间和团队空间数据模型，并为已有用户和团队补齐空间。
3. 将项目归属从 `visibility/tenant_id` 迁移到 `space_id`，兼容现有接口。
4. 扩展项目所有者字段，实现所有权转让。
5. 扩展项目协作者，加入基础角色和能力覆盖。
6. 统一项目访问策略，覆盖个人项目、团队项目、团队管理员和协作者。
7. 实现项目在个人空间和团队空间之间移动。
8. 实现团队管理员复制项目到个人空间。
9. 实现归档、恢复、30 天硬删除任务和项目级审计。
10. 补充数据库约束、并发测试、HTTP 授权测试和数据迁移验证。

## 八、必须覆盖的测试场景

- 新用户只有个人空间，不自动拥有团队成员关系。
- 用户可以创建多个团队，创建者自动成为管理员。
- 邀请只能被指定用户接受，且不能重复使用。
- 团队始终保留至少一个有效管理员。
- 团队成员可以查看团队空间项目。
- 未授权成员不能编辑项目。
- 同一项目的多个协作者可以拥有不同能力。
- `editor` 可以被单独授予或撤销 `project.archive`。
- 团队管理员可以管理团队空间项目，但不成为项目所有者。
- 项目所有者可以转让给团队内成员，不能转让给团队外用户。
- 非所有者不能将项目移回个人空间。
- 项目所有者退出团队后，项目仍留在团队空间。
- 团队管理员复制项目后，副本进入个人空间并与原项目独立。
- 归档项目可在 30 天内恢复，恢复到原空间。
- 超过 30 天的归档项目被系统硬删除，清理项目子数据和对象存储资源。
- 并发修改协作者、转让所有权、归档和复制时不会产生越权或重复数据。
