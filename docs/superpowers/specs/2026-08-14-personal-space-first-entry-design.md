# 个人空间优先进入设计

## 背景

用户登录后，服务端会在同一事务中确保其拥有唯一的个人空间；数据库也通过个人空间所有者的部分唯一索引保证一个用户最多拥有一个个人空间。当前 Web 端仍把“没有团队”视为未完成入驻，并将用户重定向到需要填写“工作空间名称”的团队创建页。这让个人空间错误地承担了团队空间的命名流程。

## 目标

- 新用户首次登录后直接进入默认的个人空间，不要求输入空间名称。
- 个人空间始终由当前用户唯一拥有，不新增名称字段，也不通过固定名称伪装成团队。
- 团队空间继续保留独立的命名和创建流程，但不再是首次使用的前置条件。
- 个人项目在没有团队时可以使用现有的个人项目 API；有团队时继续使用现有团队项目 API。

## 非目标

- 本次不重构个人空间和团队空间的数据模型。
- 本次不实现个人项目与团队空间之间的移动、复制或转让。
- 本次不设计团队切换器、团队设置页或团队邀请流程的新界面。

## 方案

### 1. 认证与首次进入

`AuthGate` 只负责确认登录状态，不再因为 `session.teams` 为空而跳转 `/onboarding`。工作台、故事入口和短剧入口均允许没有团队的已登录用户进入。

`/onboarding` 保留为显式的团队空间创建页，文案调整为团队空间语义；它不再由首次进入流程自动触发。团队创建接口继续要求名称，个人空间不经过该接口。

### 2. 个人/团队项目上下文

Web 故事工作台根据当前会话选择请求边界：

- 没有团队时，使用 `/v1/me/story-projects` 及其个人项目子资源路径。服务端从当前用户身份解析其唯一个人空间，不由客户端提交或命名个人空间。
- 有团队时，沿用 `/v1/teams/:teamId/story-projects` 及现有团队子资源路径。
- 个人项目固定为私有，团队项目继续遵循现有团队可见性与成员权限规则。

前端项目类型将允许个人项目的 `tenantId` 为 `null`，并以 `spaceKind` 区分个人/团队上下文。个人空间展示使用稳定的产品文案“个人空间”，不读取或生成可编辑名称。

短剧入口同步移除团队前置门槛；短剧当前为占位工作台，不新增个人项目 API，后续接入项目数据时复用同一上下文规则。

### 3. 唯一性与失败处理

服务端继续使用已有的 `ensurePersonalForUser` 和数据库唯一索引保证幂等创建。若个人空间读取失败，工作台显示现有错误状态并提供重试，不回退到团队命名页；这样不会把基础设施错误误判成需要创建团队。

## 测试设计

- Web：验证无团队的已登录会话不会被 `AuthGate` 重定向到 `/onboarding`；有团队的会话仍能正常加载团队工作台。
- Web：验证个人项目 API 的请求路径、个人项目 `tenantId: null` 映射，以及项目详情、成果读取和编辑继续使用正确的个人路径。
- Server：保留并运行现有个人空间唯一性、个人项目访问和团队创建测试；如接口映射有变，补充个人项目 HTTP 回归测试。
- 静态检查：运行 Web 相关测试、Web typecheck/build，以及必要的根级 lint/format 检查。

## 验收标准

1. 新用户登录后访问 `/workspace`、`/stories` 或 `/dramas` 不会被要求填写名称。
2. 新用户无需创建团队即可使用个人空间入口。
3. 个人空间没有用户可编辑的名称，且同一用户不会创建出第二个个人空间。
4. 用户主动创建团队时仍必须填写团队名称，团队空间行为不受个人空间免命名影响。
5. 没有团队的故事项目请求不依赖团队 ID，也不会把个人项目误发到团队接口。
