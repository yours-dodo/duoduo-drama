# 个人项目与团队项目共存设计

## 状态

- 状态：待实现前审阅
- 日期：2026-08-13
- 依据：C 端用户体系与权限设计、C 端用户体系数据库表设计
- 范围：让项目可以明确归属于个人空间或团队空间，并保持旧 `visibility` 接口兼容
- 非目标：本切片不实现项目复制、所有权转让、空间移动、完整归档恢复生命周期，也不一次性删除所有项目子表的 `tenant_id`

## 1. 目标与不变量

本切片完成项目空间归属的第一步：

- `story_projects.space_id` 成为项目当前归属的唯一业务来源。
- `visibility = private` 只表示项目归属于当前用户的个人空间。
- `visibility = team` 只表示项目归属于当前团队空间。
- 个人空间项目不产生有效项目协作者。
- 团队空间项目必须属于目标团队空间，项目所有者必须是该团队的有效成员。
- 个人空间项目只允许项目所有者访问、编辑、归档和管理。
- 团队空间项目继续使用团队成员、团队管理员、项目所有者和项目协作者的统一授权策略。
- 旧团队路由继续可用；新个人项目通过用户范围入口创建和查询。

以下规则不在应用层通过 `visibility` 猜测：所有授权判断先确定项目的 `space_id` 和空间类型，再执行所有者、团队成员和协作者判断。

## 2. 兼容策略

### 2.1 输入兼容

现有团队接口继续接受 `visibility`：

- 团队路由中的 `team` 映射到当前团队空间。
- 团队路由中的 `private` 不再创建“团队内私有项目”，而是映射到当前操作者的个人空间；路径中的团队只用于校验请求上下文和兼容旧客户端，不改变最终空间归属。

新增用户范围项目入口使用空间类型而不是旧 `visibility`：

- 用户范围创建接口创建个人空间项目。
- 团队范围创建接口创建团队空间项目。
- 响应暂时保留 `visibility`，由 `space.kind` 映射生成，供旧客户端继续使用。

### 2.2 数据兼容

迁移期间暂时保留 `tenant_id` 和 `visibility`：

- 新写入必须同时写入正确的 `space_id` 和兼容字段。
- 新读取以 `space_id` 为主，旧字段只用于兼容旧查询和项目子表的过渡范围。
- 个人项目的 `tenant_id` 不代表团队归属，不能用于授权判断。
- 子表本批仍可保留旧 `tenant_id`，但查询必须先加载根项目并通过项目授权；后续切片再移除子表对团队的硬依赖。

如果当前数据库约束不允许个人项目使用空团队归属，迁移必须先将项目根表及相关复合外键调整为可表达个人项目的形式；不得创建虚拟团队来绕过目标模型。

## 3. 应用层设计

### 3.1 空间解析

新增应用层空间解析端口或服务，统一完成：

```text
个人范围
  → 查询当前用户的 personal space
  → 校验 space.owner_user_id = actor_user_id

团队范围
  → 校验 actor 是目标团队有效成员
  → 查询目标 team space
  → 校验 project.create 的团队权限
```

解析结果至少包含：

```text
spaceId
spaceKind: personal | team
teamId: string | null
ownerUserId: string | null
```

项目创建、列表、读取、更新和归档都使用该解析结果或项目自身的 `space_id`，不在 Controller 中重复判断。

### 3.2 项目创建

个人空间创建：

```text
锁定个人空间
  → 校验空间属于当前用户
  → 以个人范围生成幂等 scope
  → 创建项目，space_id 指向个人空间，owner_user_id 为当前用户
  → 不创建协作者
  → 写入项目审计
```

团队空间创建：

```text
锁定团队和当前成员关系
  → 校验目标团队空间
  → 校验 project.create
  → 以团队范围生成幂等 scope
  → 创建项目，space_id 指向团队空间，owner_user_id 为当前用户
  → 写入项目审计
```

`created_by_user_id` 永远保存首次创建者，不随空间归属或未来所有权转让改变。

### 3.3 项目读取与授权

统一策略按以下顺序执行：

1. 读取项目及其 `space_id`。
2. 个人空间：只允许 `owner_user_id` 等于当前用户。
3. 团队空间：要求当前用户是团队有效成员。
4. 团队管理员拥有隐式项目管理能力，但不成为项目所有者或协作者。
5. 普通成员按团队默认查看范围和项目协作者权限判断。
6. 归档状态在操作级别单独判断。

个人空间项目即使旧字段残留 `tenant_id`，也不能被该团队的其他成员、管理员或历史协作者访问。

### 3.4 接口边界

保留：

- `POST /v1/teams/:teamId/story-projects`
- `GET /v1/teams/:teamId/story-projects`
- 现有项目详情、更新、归档和协作者接口

新增用户范围项目入口：

- `POST /v1/me/story-projects`
- `GET /v1/me/story-projects`

项目详情等操作最终应迁移到不依赖团队上下文的项目资源入口；本切片可以先保留旧路由，同时让应用层通过项目 `space_id` 验证请求上下文，禁止用路径中的 `tenantId` 替代空间授权。

## 4. 持久化与迁移

### 4.1 根项目表

目标字段至少包含：

```text
space_id
created_by_user_id
owner_user_id
visibility        # 兼容字段，暂不作为授权事实
tenant_id         # 过渡字段，暂不作为空间事实
```

迁移必须满足：

- 现有团队项目按 `tenant_id` 回填对应团队空间。
- 现有项目按产品确认的归属规则回填 `owner_user_id`。
- 新建个人项目不依赖虚拟团队记录。
- 迁移过程中同时校验 `space.kind`、`space.owner_team_id`、`space.owner_user_id` 与项目输入一致。

### 4.2 项目子表

本切片暂不直接重写所有子表结构，但必须建立访问边界：

- 对话、消息、资产、成果和生成请求先由根项目授权，再执行子表查询。
- 子表的 `tenant_id` 只能作为过渡查询键，不得单独授权。
- 后续迁移应逐步改为仅通过 `project_id`、`conversation_id` 或 `artifact_id` 关联根项目。

### 4.3 Migration 基线风险

当前历史 migration 已被清理，因此本切片新增 migration 只能表达从现有数据库到目标结构的增量变化。部署前必须单独完成以下一项：

- 恢复完整历史 migration；或
- 基于当前完整 schema 生成并审阅新的 baseline migration。

在 baseline 未确定前，不宣称全新数据库可以通过 `prisma migrate deploy` 初始化。

## 5. 错误与事务边界

- 个人空间不存在：视为空间初始化异常，不静默创建虚拟团队。
- 团队成员无效：拒绝创建团队项目。
- 项目与请求空间不一致：返回资源不可见或访问拒绝，避免泄露项目存在性。
- 个人项目存在有效协作者：创建或迁移时拒绝，不能继续产生新的访问关系。
- 空间归属、项目写入、幂等记录和审计记录必须在同一事务中提交。
- 重放同一个幂等键只能返回同一个项目，不能生成第二个项目或跨空间复用结果。

## 6. 测试验收

### 领域与应用测试

- `private` 项目落到当前用户个人空间。
- `team` 项目落到目标团队空间。
- 个人空间项目不创建协作者。
- 团队成员可以访问团队项目，但未授权成员不能编辑。
- 团队管理员可以管理团队项目，但不是项目所有者。
- 其他用户不能通过残留 `tenant_id` 访问个人项目。
- 同一用户范围幂等键重放不会创建第二个个人项目。
- 团队范围与用户范围使用不同幂等 scope，不能互相复用结果。

### HTTP 测试

- 个人项目创建和列表接口。
- 团队项目创建和列表接口保持兼容。
- 个人项目详情、更新、归档的所有者授权。
- 团队成员、管理员、协作者的跨空间访问拒绝。
- 个人项目添加协作者被拒绝。

### PostgreSQL 迁移测试

- 个人空间和团队空间的归属约束有效。
- 项目 `space_id` 与空间类型不一致时事务失败。
- 迁移回填后的旧团队项目仍可访问。
- 个人项目不会因为旧 `tenant_id` 残留而获得团队访问权。
