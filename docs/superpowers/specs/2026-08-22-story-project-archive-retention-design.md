# 故事项目归档、恢复与 30 天永久清理设计

## 设计结论

故事项目采用“立即归档、保留 30 天、到期自动永久清理”的生命周期。

归档是可恢复的软删除。归档后项目不再允许编辑、生成、上传或新增协作者，但在 30 天保留期内仍可由有权用户恢复。达到清理时间后，Server 内部清理任务删除项目数据库内容和对象存储文件；永久清理不向普通 HTTP 调用方开放，也不支持恢复。

现有 `POST .../archive` 接口、项目归档权限和 `status: 'archived'` 状态继续使用。本设计补齐前端入口、归档时间、清理时间、恢复能力和后台清理执行器。

## 目标

- 用户可以从故事项目界面明确归档一个故事；
- 归档项目保留 30 天，并清楚显示最终清理时间；
- 归档期内允许恢复，恢复后继续沿用原项目 ID 和全部内容；
- 到期项目由 Server 自动、批量、可重试地永久清理；
- 永久清理覆盖故事成果、版本、角色资产、对话、生成任务、导入任务、协作者、上传资产记录和对象存储文件；
- 个人空间和团队空间继续遵守现有项目授权边界；
- 清理失败不得把项目误报为已删除，也不得阻塞其他到期项目。

## 非目标

- 首期不提供用户主动“立即永久删除”接口；
- 首期不提供自定义保留天数；
- 首期不删除用户、团队、空间或团队成员关系；
- 首期不删除安全审计记录；审计只保留目标 ID、动作和最小摘要，不保留故事正文或资产文件；
- 首期不引入外部队列、Cron 服务或新的定时任务依赖。

## 生命周期

```text
active
  │ 归档
  ▼
archived ── 30 天内恢复 ──▶ active
  │
  │ purgeAt 到期
  ▼
purging（由 purgeStartedAt 表示）
  │ 数据库内容与对象存储均清理成功
  ▼
不存在（永久删除）
```

对外仍只暴露 `active` 和 `archived`。`purging` 不新增项目 `status` 枚举值，而是由非空的 `purgeStartedAt` 表示清理占用；被占用项目不进入普通项目列表，也不作为可编辑状态返回。

### 归档时间

项目新增以下字段：

```ts
archivedAt: Date | null;
purgeAt: Date | null;
purgeStartedAt: Date | null;
```

- 新项目三个字段均为 `null`；
- 首次归档时，`archivedAt = databaseNow`；
- `purgeAt = archivedAt + 30 * 24 小时`；
- 对已经归档的项目重复归档是幂等操作，不延长保留期；
- 恢复后清空三个字段；
- 到达 `purgeAt` 表示项目可被清理，实际清理时间允许落在下一次小时扫描内。

所有时间计算使用数据库时钟，避免应用实例时钟偏差。

数据库迁移为活跃项目写入三个 `null` 字段。对迁移前已经归档的项目，以迁移执行时的数据库时间作为 `archivedAt`，并重新给予完整 30 天保留期，避免部署后立即清理历史归档数据。数据库增加 `(status, purgeAt)` 索引支持到期扫描。

## 权限

### 归档

沿用现有 `canArchiveProject` 规则：

- 个人项目：仅项目所有者；
- 团队项目：项目所有者、团队管理员，或具有 `project.archive` 权限的项目协作者；
- 已归档项目重复调用归档接口返回当前状态，不刷新 30 天期限。

### 恢复

恢复权限与归档权限一致，但针对归档项目计算。归档项目已不具备编辑能力，因此恢复不能复用 `canEditProject`。

- 个人项目仅所有者可恢复；
- 团队项目沿用归档时的所有者、团队管理员和 `project.archive` 权限；
- 已达到 `purgeAt` 但尚未被清理的项目不再允许恢复，返回 `410 Gone`；
- 清理执行器已经占用的项目不允许恢复。

### 永久清理

永久清理没有公开 HTTP 接口。只有 Server 内部保留任务可以执行，不接收用户身份或项目 ID 参数。

## HTTP 与输出契约

保留现有接口：

```text
POST /v1/me/story-projects/:projectId/archive
POST /v1/teams/:teamId/story-projects/:projectId/archive
```

新增恢复接口：

```text
POST /v1/me/story-projects/:projectId/restore
POST /v1/teams/:teamId/story-projects/:projectId/restore
```

归档和恢复请求都携带 `expectedRevision`，继续使用项目乐观并发控制。响应中的项目增加：

```ts
archivedAt: string | null;
purgeAt: string | null;
canArchive: boolean;
canRestore: boolean;
```

错误语义：

- `404`：项目不存在，或调用方无权查看；
- `409`：项目修订号冲突；
- `410`：恢复期限已到或项目正在永久清理；
- `500/503`：清理基础设施失败，仅记录在服务端，普通用户不会收到永久清理接口错误。

## 前端交互

### 活跃项目

项目页面提供“归档故事”危险操作。按钮仅在 `canArchive` 为真时出现。

确认框文案明确说明：

```text
归档“故事名”？
归档后将停止编辑，并在 30 天后永久删除全部故事内容和素材。保留期内可以恢复。
```

归档成功后返回故事列表，并重新加载服务端项目数据，不通过前端伪造状态。

### 归档项目

故事列表继续显示归档项目，但归档卡片与活跃项目明确区分，并展示 `将于 YYYY-MM-DD 永久删除`。归档卡片不再链接到编辑工作台，恢复操作直接显示在卡片上。

归档项目提供“恢复故事”按钮。恢复成功后重新进入原项目，项目 ID、路由和全部内容保持不变。

### 状态与错误

- 归档、恢复过程中禁用重复提交；
- 修订冲突提示用户刷新后重试；
- 恢复期限已到时移除恢复按钮并刷新列表；
- 服务端失败显示真实操作失败信息，不再统一提示“检查网络”。

## 后台清理执行器

### 运行方式

`StoryProjectRetentionService` 随 Server 启动，并在以下时机调用清理用例：

- Server 启动完成后执行一次；
- 此后每小时执行一次；
- Server 关闭时释放定时器；
- 单次最多占用 20 个项目，避免大批量清理长期占用数据库连接。

执行器不引入新的调度依赖。清理用例保持独立，可由测试或未来外部 Cron 直接调用。

### 并发占用

扫描使用数据库条件更新或 `FOR UPDATE SKIP LOCKED` 获取到期项目，并写入 `purgeStartedAt`。只有满足以下条件的项目可被占用：

```text
status = archived
purgeAt <= databaseNow
purgeStartedAt 为空，或早于 databaseNow - 2 小时
```

占用具有两小时超时恢复能力。实例在清理中途退出后，后续扫描可以重新占用过期任务。对象存储删除必须按幂等操作处理，因此重复执行不会损坏其他项目。

## 永久清理流程

每个项目独立处理，单个项目失败不回滚已经成功清理的其他项目。

1. 再次读取并校验项目仍为到期归档状态；
2. 读取项目全部资产记录和 `objectKey`；
3. 逐个删除对象存储文件；对象不存在视为已删除；
4. 对象存储全部成功后，开启数据库事务；
5. 按外键安全顺序删除项目数据；
6. 在同一事务中写入一次不含故事内容的 `STORY_PROJECT_PURGED` 审计事件；
7. 删除项目本身并提交事务；
8. 任一步失败时保留项目和 `purgeAt`，记录受控错误，等待后续扫描重试。

对象存储先于数据库删除。若对象删除成功但数据库事务失败，下一次重试会再次执行幂等对象删除，然后重试数据库事务。这样不会出现数据库已经确认永久删除、对象文件却永久失去重试依据的情况。

### 数据库清理范围

事务必须处理以下项目范围数据：

- 角色资产及封面图、人物视图引用；
- 故事成果当前版本指针、成果版本和成果模块；
- 生成请求对消息、成果和成果版本的可空引用；
- 对话消息、生成请求和对话；
- 故事导入任务；
- 项目协作者及权限覆盖；
- 项目资产记录；
- 以项目或其子资源为 `resultId` 的幂等记录；
- 故事项目行。

清理顺序由单一的项目清理仓储封装，业务用例不散落具体表名。现有外键继续默认 `Restrict`，仅对天然从属且没有独立生命周期的关系保留或使用 `Cascade`；关键内容删除由显式事务完成，避免未来新增子表时被无声遗漏。

### 审计保留

安全审计记录不参与项目内容清理。永久清理事件只记录项目 ID、租户/空间、清理时间和资源计数，不记录标题、正文、对话或文件名。这样可以证明清理发生，同时不保留可恢复的故事内容。

## 领域与模块边界

- `StoryProject` 领域对象负责归档、恢复、修订号和保留时间不变量；
- `ArchiveStoryProject` 继续负责用户发起的归档；
- 新增 `RestoreStoryProject` 负责授权和恢复；
- 新增 `PurgeArchivedStoryProjects` 负责扫描、占用、重试和批次编排；
- 项目清理仓储负责数据库级项目内容清理；
- `ObjectStorage` 继续负责文件删除；
- `StoryProjectRetentionService` 只负责触发周期，不包含业务规则；
- Web 只调用公开归档/恢复接口，不参与 30 天计算。

## 可观测性与失败处理

清理执行器至少记录：

- 本次扫描发现、占用、成功和失败的项目数量；
- 项目 ID、租户 ID、尝试时间和稳定失败码；
- 对象存储删除失败与数据库事务失败的区分；
- 单批次执行耗时。

日志不得包含故事正文、消息正文、对象签名 URL 或凭据。重复失败不会修改 `purgeAt`，避免错误无限延长保留期。

## 测试策略

### 领域测试

- 归档设置 `archivedAt`、`purgeAt` 并递增修订号；
- 重复归档不延长 `purgeAt`；
- 保留期内恢复并清空归档字段；
- 到期或清理占用后拒绝恢复；
- 活跃、归档状态下的编辑限制保持正确。

### 应用测试

- 个人和团队权限分别覆盖允许、拒绝路径；
- 归档、恢复均覆盖修订冲突；
- 批次扫描只占用到期项目；
- 一个项目失败不阻塞同批次其他项目；
- 对象存储失败后项目仍可被下一轮重试；
- 重复清理保持幂等。

### PostgreSQL 集成测试

- 使用包含角色资产、成果版本、对话消息、生成请求、导入任务、协作者和上传资产的完整项目夹具；
- 清理后项目及所有范围内子资源均不存在；
- 其他项目、用户、团队和空间数据保持不变；
- 安全审计记录保留且不包含故事内容；
- 并发清理不会重复删除或跨项目删除。

### Web 测试

- 个人和团队归档请求使用正确路径；
- 归档确认文案包含 30 天和永久删除提示；
- 归档成功后返回列表并刷新数据；
- 归档卡片显示永久删除日期和恢复按钮；
- 恢复成功后回到原项目；
- 冲突、到期和网络/服务端错误显示不同提示。

## 验收标准

- 活跃故事可以通过界面归档；
- 归档时服务端写入数据库时钟生成的 `archivedAt` 和 30 天后的 `purgeAt`；
- 归档项目不可编辑，但在到期前可以恢复；
- 到期项目最迟在下一次小时扫描中进入清理；
- 永久清理删除项目的成果、版本、角色资产、对话、任务、协作者、资产记录和对象存储文件；
- 清理失败可自动重试，不误删其他项目；
- 个人空间和团队空间的权限边界不变；
- 单元测试、HTTP 测试、PostgreSQL 集成测试、Web 测试、类型检查和构建全部通过。
