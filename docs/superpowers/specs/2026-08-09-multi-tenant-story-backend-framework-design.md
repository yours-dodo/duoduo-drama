# 多租户故事创作后端框架设计

> 状态：设计已确认，实施计划已编制
>
> 日期：2026-08-09
>
> 实施：[多租户故事创作后端实施计划](../plans/2026-08-09-multi-tenant-story-backend-implementation-plan.md)

## 1. 文档目标

本文面向负责后端实现和评审的工程师。读者完成阅读后，应能据此拆分并实施首个多租户故事创作后端，而不需要重新决定服务边界、租户模型、认证方式、核心数据关系或 Agent 接入方式。

首个交付目标是建立可运行、可持久化、可测试的业务后端和 HTTP API 骨架。它需要支持用户通过邮箱登录，在多个团队空间中工作，创建故事项目和创作对话，产生模拟草稿，并将草稿确认为不可变版本。

## 2. 范围与非目标

### 2.1 首期范围

首期包含：

- NestJS 模块化单体业务服务。
- PostgreSQL 业务数据库和受版本控制的迁移。
- 无密码邮箱验证码或魔法链接登录。
- 用户创建团队、通过邀请加入团队，以及在多个团队间切换工作上下文。
- 团队级租户隔离、团队成员角色、项目可见范围和项目协作者权限。
- 故事项目、创作对话、消息、草稿成果和确认版本。
- 统一错误、请求追踪、幂等、乐观并发和审计记录。
- Agent 集成端口和可预测的模拟实现。
- 领域单元测试、PostgreSQL 集成测试和 HTTP 端到端测试。

### 2.2 明确不做

首期不包含：

- 真实模型或 Agent 服务调用。
- Redis、任务队列、实时推送和通知中心。
- 文件上传、对象存储、剧本解析和素材管理。
- 短剧项目、剧集、场景、镜头和制作流程。
- 计费、额度、企业单点登录和第三方身份提供商。
- PostgreSQL 行级安全、每租户独立 Schema 或每租户独立数据库。
- 生产邮件服务商选型；首期通过邮件发送端口接入本地或测试适配器。

这些能力均保留扩展边界，但不得为了未来需求提前引入对应基础设施。

## 3. 总体架构

后端采用模块化单体。Web 和未来移动端只访问业务 Server；业务 Server 是身份、租户、权限和业务数据的权威。Agent 不能直接访问业务数据库，只能通过明确的集成协议获取已经授权的数据。

```text
Web / 未来移动端
        │
        ▼
NestJS Business Server
├── Platform
├── Identity
├── Tenancy
├── Authorization
├── Story Creation
├── Audit
└── Agent Integration
        │
        ├── PostgreSQL Business Database
        ├── Email Delivery Port → Local/Test Adapter
        └── Agent Gateway → Mock Adapter
                              └── Future HTTP Agent Adapter
```

业务 Server 与 Agent 可以使用同一 PostgreSQL 集群，但必须使用独立数据库和独立凭据。两者通过业务标识和协议关联，不共享表、ORM 模型或数据库账号。

### 3.1 模块职责

| 模块              | 职责                                                                 | 不负责                          |
| ----------------- | -------------------------------------------------------------------- | ------------------------------- |
| Platform          | 配置校验、数据库连接、事务、统一错误、请求编号、日志、存活与就绪检查 | 业务规则                        |
| Identity          | 用户、邮箱登录挑战、登录会话                                         | 团队权限和项目权限              |
| Tenancy           | 团队、成员关系、邀请、当前租户解析                                   | 故事内容                        |
| Authorization     | 团队角色、项目可见范围、协作者策略                                   | 身份验证和数据持久化            |
| Story Creation    | 故事项目、对话、消息、草稿成果和确认版本                             | Agent 执行细节                  |
| Audit             | 敏感操作审计记录和管理员查询                                         | 普通运行日志                    |
| Agent Integration | Agent 请求映射、授权上下文、超时、幂等和结果映射                     | 提示词、模型选择和 Agent 工作流 |

### 3.2 依赖方向

控制器只负责验证传输输入、调用一个应用用例并映射 HTTP 响应。应用用例协调领域对象、授权策略、事务和外部端口。领域对象不依赖 NestJS、HTTP DTO、Prisma 类型或 Agent 协议。

基础设施实现数据库、邮件和 Agent 端口。模块之间通过公开应用服务或明确端口协作，不直接读取其他模块的内部表。首期不创建共享 contracts 包；只有协议稳定且出现第二个真实消费者后，才考虑生成客户端或提取共享契约。

## 4. 多租户、身份、授权与审计

### 4.1 租户模型

团队空间就是租户。用户是全局身份，同一用户可以通过成员关系加入多个团队。所有项目、对话、消息、成果、版本、生成请求和业务审计记录都必须属于一个团队。用户、登录挑战、会话和身份安全事件是全局身份数据，不归属任何团队，也不得引用租户业务资源。

客户端通过团队资源路径选择工作上下文，例如 `/v1/teams/{teamId}/story-projects`。服务端验证登录会话和团队成员关系后建立不可变的请求租户上下文。客户端提供的团队 ID 只是候选值，不能自行赋予访问权。

服务端不在用户会话中保存全局“当前团队”。客户端通过切换团队路径改变工作上下文，因此不同设备和同一用户的并行请求不会互相覆盖租户选择。

每个租户数据表都保存非空 `tenantId`。跨表关联使用包含 `tenantId` 的复合唯一约束和复合外键，防止数据库中出现跨租户引用。仓储查询必须显式接收租户上下文，不提供无租户条件的普通业务查询方法。

跨租户访问统一表现为资源不存在，避免泄露其他团队的资源标识。首期以应用层隔离和数据库约束为主；需要强合规隔离时，再评估 PostgreSQL 行级安全或独立数据库。

### 4.2 身份与登录

用户使用邮箱验证码或魔法链接登录，不设置密码。两种入口使用同一种一次性、不透明登录令牌：邮件可以同时展示验证码并携带链接，验证接口只消费一次令牌。

登录挑战默认十分钟过期，只在数据库中保存令牌哈希、目标邮箱、过期时间、尝试次数和消费时间。发送和验证操作按邮箱与来源地址限流，响应不能暴露邮箱是否已注册。未注册邮箱在首次成功验证时创建用户，不需要独立注册步骤。

验证成功后创建登录会话。Web 首期使用 `HttpOnly`、`SameSite=Lax` Cookie，生产环境强制 `Secure`；数据库只保存会话令牌哈希。所有写请求还必须验证可信 `Origin`，防止 Cookie 会话被跨站滥用。登出或管理员撤销会话后，令牌立即失效。移动端 Bearer Token 在移动端接入阶段设计，不与 Web Cookie 方案提前混合。

首次登录的用户可以创建团队，也可以通过邀请加入团队。团队创建者自动成为第一个管理员，最后一个有效管理员不能被移除或降级。邀请令牌同样只保存哈希并设置有效期；接受邀请时，登录邮箱必须与受邀邮箱一致。

### 4.3 权限规则

系统级团队角色保持两类：`admin` 和 `member`。项目级协作者不是团队角色。

| 身份         | 团队项目               | 私人项目         | 成员与邀请       | 审计查询       |
| ------------ | ---------------------- | ---------------- | ---------------- | -------------- |
| 团队管理员   | 查看、编辑、管理       | 查看、编辑、管理 | 管理             | 允许           |
| 项目创建者   | 查看、编辑、管理协作者 | 查看、编辑       | 不能管理团队成员 | 仅项目相关记录 |
| 项目协作者   | 查看、编辑             | 无访问权         | 不允许           | 不允许         |
| 其他普通成员 | 仅查看                 | 无访问权         | 不允许           | 不允许         |

项目变为私人范围时，当前协作者关系在同一事务中撤销并保留撤销时间用于审计。项目恢复团队范围时不会自动恢复旧协作者，必须由项目创建者或团队管理员重新邀请。任何权限判断都以当前团队成员关系和当前项目状态为准，不能缓存为长期不变的布尔字段。

### 4.4 审计规则

以下行为必须在同一数据库事务内写入业务变更和审计记录：

- 团队成员邀请、加入、角色变化和移除。
- 项目可见范围变化和项目协作者变化。
- 管理员查看、修改或归档私人项目。
- 草稿成果确认和当前有效版本变化。
- 团队范围内的安全和权限操作。

审计记录至少包含租户、操作者、动作、目标类型与标识、变化前后摘要、请求编号和发生时间。审计内容不能保存登录令牌、会话令牌、模型密钥或完整敏感正文。

登录挑战锁定、会话撤销等无法归属单一团队的操作写入独立的全局身份安全事件。该记录只包含用户、会话、动作、请求编号和时间等安全元数据，不提供租户业务审计 API。

## 5. 故事创作数据模型

### 5.1 核心关系

```text
User ──< TeamMembership >── Team
Team ──< StoryProject ──< Conversation ──< Message
                    ├──< StoryResult
                    ├──< StoryVersion
                    └──< StoryGenerationRequest
```

核心对象如下：

- `StoryProject`：保存团队、创建者、标题、团队或私人可见范围、生命周期状态、当前有效版本和并发修订号。
- `ProjectCollaborator`：保存团队项目与可编辑成员的关系；项目私人化后不产生有效权限。
- `Conversation`：属于一个故事项目，保存标题、正常或归档状态和并发修订号。
- `Message`：属于一个对话，记录用户、Agent 或系统消息及来源。消息追加后不可原地改写。
- `StoryGenerationRequest`：记录一次由用户消息触发的草稿生成请求、状态、幂等键、输入快照和可选 Agent Task 标识。
- `StoryResult`：保存一次生成或人工编辑形成的草稿成果、来源关系、内容和修订号。状态为 `draft`、`confirmed` 或 `discarded`。
- `StoryVersion`：保存确认时的不可变内容快照、项目内递增版本号、确认人、来源草稿和来源对话。

### 5.2 生命周期与不变量

首期底层 API 显式创建项目和对话，不在消息接口中隐式猜测租户或项目归属。Web 仍可在用户首次发送消息时依次调用创建项目、创建对话和追加消息接口，实现产品层的自动创建体验。

故事项目和对话可以归档。归档对话不会删除已经产生的草稿和版本；归档项目保留全部版本与审计历史。首期不提供确认版本的物理删除。

草稿可在确认前编辑，每次修改必须携带预期修订号。确认草稿时，服务端在一个事务内：

1. 校验租户、项目编辑权限、草稿状态和预期修订号。
2. 创建不可变的 `StoryVersion` 快照。
3. 将草稿标记为已确认。
4. 更新项目的当前有效版本引用和修订号。
5. 写入审计记录。

重复确认同一草稿必须返回同一个已确认版本，不能创建重复版本。确认另一个仍处于 `draft` 状态的较早草稿可以生成新项目版本，但不会修改已有版本内容。

## 6. API、并发与 Agent 占位

### 6.1 HTTP 约定

首期使用版本化 JSON API，统一前缀为 `/v1`。输入通过 DTO 做结构和字段校验；输出不暴露数据库模型。列表接口采用游标分页，并使用稳定排序字段。

统一错误结构为：

```json
{
  "error": {
    "code": "STORY_PROJECT_REVISION_CONFLICT",
    "message": "项目已被其他操作更新",
    "requestId": "request-id",
    "details": []
  }
}
```

`code` 是稳定的机器可读业务错误码；`message` 可以展示给用户；`details` 只包含安全的字段问题；`requestId` 用于排查。内部异常、数据库错误和外部服务响应不得直接返回客户端。

### 6.2 首批接口组

| 接口组                                                                                  | 主要能力                           |
| --------------------------------------------------------------------------------------- | ---------------------------------- |
| `/v1/auth`                                                                              | 请求邮箱登录、验证令牌、登出       |
| `/v1/me`                                                                                | 当前用户、有效会话和可访问团队     |
| `/v1/teams`                                                                             | 创建和列出团队                     |
| `/v1/teams/{teamId}/members`                                                            | 成员列表和管理员成员管理           |
| `/v1/teams/{teamId}/invitations`                                                        | 创建、查看和撤销邀请               |
| `/v1/team-invitation-acceptances`                                                       | 当前登录邮箱接受一次性团队邀请     |
| `/v1/teams/{teamId}/story-projects`                                                     | 项目创建、列表、详情、修改和归档   |
| `/v1/teams/{teamId}/story-projects/{projectId}/conversations`                           | 对话创建、列表、重命名和归档       |
| `/v1/teams/{teamId}/story-projects/{projectId}/conversations/{conversationId}/messages` | 消息追加和读取                     |
| `/v1/teams/{teamId}/story-projects/{projectId}/results`                                 | 草稿读取、编辑、放弃和确认         |
| `/v1/teams/{teamId}/story-projects/{projectId}/versions`                                | 当前版本和版本历史                 |
| `/v1/teams/{teamId}/story-projects/{projectId}/generation-requests`                     | 查询生成状态和重试失败或未完成请求 |
| `/v1/teams/{teamId}/audit-records`                                                      | 授权范围内的审计查询               |

详细字段和 OpenAPI 契约在实施计划中按切片定义。资源命名、租户路径和错误结构属于本设计的稳定边界。

### 6.3 幂等与并发

创建团队、发送邀请、创建项目、追加用户消息和确认草稿等非幂等写操作必须接受 `Idempotency-Key`。创建团队以“用户 + 操作类型 + 幂等键”为作用域；其他租户内操作再加入 `tenantId`。服务端保存请求摘要与结果引用。同一键配合同一输入时返回原结果；同一键配合不同输入时返回冲突。

可编辑聚合保存整数修订号。修改项目、对话或草稿时，客户端提交 `expectedRevision`。修订号不匹配时返回 `409`，不自动覆盖其他用户的修改。

### 6.4 模拟 Agent 流程

追加用户消息时，服务端先在一个事务中保存消息和 `StoryGenerationRequest`。随后在事务外调用 `StoryDraftGenerator` 端口。首期模拟适配器根据固定输入生成可预测结果；成功后在第二个事务中保存 Agent 消息和草稿，并将请求标记为成功。失败时记录安全的失败分类并允许使用原请求标识重试。如果进程在两个事务之间退出，重复原幂等请求或调用生成重试接口会接续原 `StoryGenerationRequest`，不会重复创建用户消息。

模拟实现可以在当前 HTTP 请求内完成并返回成功结果。未来真实 Agent 适配器可以返回已接受状态并异步完成，不需要改变故事项目、对话、草稿和确认版本的数据模型。

Agent 请求必须包含经过 Server 授权的租户、用户、项目、能力范围、幂等键和输入快照引用。Agent 只能通过 Server 提供的工具或 API 读取和修改业务数据，不能获得业务数据库凭据。

## 7. 数据库、运行与安全基线

### 7.1 PostgreSQL 与迁移

业务数据库使用 PostgreSQL，Prisma 负责类型化访问和迁移历史。迁移文件是数据库结构变更的唯一来源；应用启动不能自动同步或重建生产 Schema。生产部署先执行迁移检查与显式部署，再启动新版本服务。

所有主键使用 UUID。租户表建立以 `tenantId` 开头的查询索引；业务唯一约束包含 `tenantId`；租户内关联使用复合外键。时间由数据库记录，所有可编辑聚合保存创建时间、更新时间和修订号。

业务变更和审计、草稿确认和项目当前版本更新、消息和生成请求创建必须使用数据库事务。外部邮件和 Agent 调用不得放在长事务内。

### 7.2 配置与可观测性

服务启动时校验端口、数据库连接、Cookie 密钥、公开地址、邮件适配器和运行环境。配置缺失时启动失败，不使用静默默认值进入生产。

每个请求生成或接收请求编号，日志采用结构化字段并包含服务、环境、请求、租户和用户标识。日志不得包含登录令牌、Cookie、Authorization、模型密钥或完整创作正文。

服务提供存活与就绪检查。存活只表示进程正常；就绪检查验证业务数据库等必要依赖。首期不引入独立指标、链路追踪或告警平台，但日志字段和请求编号需要为后续接入保留稳定语义。

### 7.3 延后基础设施的触发条件

- 接入真实 Agent 或出现长时间任务时，引入耐久异步交付机制和面向产品的任务状态。
- 文件上传与生成媒体进入范围时，引入对象存储、签名访问和文件安全检查。
- 多实例实时通知或高频缓存需求出现时，再评估 Redis。
- 出现强合规租户时，再评估 PostgreSQL 行级安全、独立 Schema 或独立数据库。
- Server 与 Agent 协议稳定并出现多个消费者时，再采用 OpenAPI 或 JSON Schema 生成客户端。

## 8. 测试策略

领域单元测试覆盖项目可见性、协作者权限、草稿状态和版本不变量。应用用例测试覆盖事务边界、幂等、乐观并发、审计和外部端口失败。PostgreSQL 集成测试使用真实迁移验证复合约束、跨租户拒绝和事务回滚。

HTTP 端到端测试至少覆盖：

- 用户通过本地邮件适配器完成无密码登录。
- 同一用户创建并切换多个团队。
- 两个团队使用相同资源标识探测时不能互相读取或修改数据。
- 团队管理员、项目创建者、协作者和只读成员得到正确权限。
- 普通成员无法发现私人项目，管理员访问私人项目会产生审计记录。
- 重复幂等请求不产生重复团队、消息、邀请或版本。
- 并发修改返回修订冲突。
- 模拟 Agent 成功和失败时，消息、生成请求和草稿状态保持一致。
- 归档对话或项目不会删除已确认版本。

## 9. 分阶段实施顺序

### 阶段 1：Server 平台基座

建立配置校验、统一响应与错误、请求编号、结构化日志、API 版本前缀、DTO 校验、存活与就绪检查。验收标准是服务在合法配置下启动，在缺失关键配置时明确失败，并能输出不泄密的统一错误。

### 阶段 2：PostgreSQL 与持久化边界

接入 Prisma、首个迁移、事务端口和测试数据库。建立租户复合约束、迁移命令和数据库集成测试基座。验收标准是空数据库可重复迁移到最新版本，测试可验证跨租户外键被数据库拒绝。

### 阶段 3：无密码身份

实现用户、登录挑战和会话，接入本地邮件适配器。验收标准是新邮箱可通过验证自动建立用户和会话，失效、超限或已消费令牌不能复用，写请求具备 Cookie 跨站防护。

### 阶段 4：团队租户、授权与审计

实现团队、成员、邀请、请求租户上下文、团队角色和审计模块。验收标准是用户可创建多个团队、接受匹配邮箱的邀请，最后一个管理员不能被移除，跨租户请求不泄露资源，敏感操作与审计原子提交。

### 阶段 5：故事项目与对话

实现故事项目、项目权限策略、协作者、对话和消息 API，包括归档、游标分页、幂等与修订冲突。验收标准是团队管理员、项目创建者、协作者和只读成员符合权限矩阵，私人项目和归档操作不会泄露或破坏历史数据。

### 阶段 6：草稿、版本与模拟 Agent

实现生成请求、模拟草稿、草稿编辑、确认版本和当前版本切换。验收标准是同一输入产生可预测草稿，重复确认不创建重复版本，确认事务保持数据与审计一致。

### 阶段 7：契约与整体验收

补齐 OpenAPI、全链路端到端测试、失败路径和运行文档。验收标准是根级测试、类型检查、代码检查、构建和格式检查全部通过，且以下 MVP 场景可重复演示：用户登录，进入两个相互隔离的团队，创建故事项目和对话，发送消息得到模拟草稿，编辑并确认版本，再查看版本与审计历史。

## 10. 完成定义

满足以下条件后，首个后端框架里程碑才算完成：

- 团队作为租户边界贯穿数据库、授权、日志和 API。
- 同一用户可加入多个团队，且跨租户读取、写入和关联均被阻止。
- 邮箱无密码登录、团队邀请和安全会话可通过测试适配器完整运行。
- 团队项目与私人项目遵守已确认的角色和协作者规则。
- 故事项目、对话、消息、草稿和确认版本拥有真实 PostgreSQL 持久化。
- 所有关键写操作具备幂等、并发冲突和审计行为。
- 模拟 Agent 可替换为未来 HTTP Agent 适配器，业务模块不依赖 Agent 实现。
- Server 与 Agent 使用独立数据边界，Agent 不具备业务数据库访问权。
- 单元、数据库集成和 HTTP 端到端测试通过仓库标准检查。
